# ВЫПУСКНАЯ КВАЛИФИКАЦИОННАЯ РАБОТА

## Визуализация науки на основе метаданных публикаций и журналов

---

## АННОТАЦИЯ

Выпускная квалификационная работа посвящена разработке веб-приложения для анализа и визуализации научных публикаций по метаданным из открытых источников. Были решены задачи автоматической загрузки данных через API OpenAlex, построения реляционной базы данных PostgreSQL, геокодирования организаций авторов, создания интерактивной карты и графа связей, а также разработки серверного API и браузерного интерфейса. Результат — работающее веб-приложение, позволяющее видеть научный ландшафт в виде географической карты и графа связей между публикациями, авторами, журналами и организациями.

**Ключевые слова:** визуализация данных, научные публикации, OpenAlex, PostgreSQL, геокодирование, граф связей, веб-приложение.

## ВВЕДЕНИЕ

### Актуальность

Наука сегодня производит огромное количество публикаций: по данным каталога OpenAlex, в открытом доступе находится более 250 миллионов научных работ. Когда статей так много, привычный поиск по ключевым словам помогает найти конкретный материал, но не отвечает на вопросы шире: кто с кем сотрудничает, какие университеты активнее всего публикуются по теме, как менялась тематика за последние годы.

Если перевести метаданные публикаций в визуальные форматы — карту и граф — становится видно то, что иначе скрыто в тысячах строк: географию исследований, авторские коллаборации, тематические кластеры. Именно это и решает данный проект.

### Постановка задачи

**Объект исследования** — система метаданных научных публикаций и журналов, представленных в открытых библиографических каталогах.

**Предмет исследования** — методы интерактивной визуализации метаданных научных публикаций: географической карты аффилиаций авторов и графа связей между публикациями, авторами, журналами и организациями.

**Цель работы** — разработать веб-приложение для интерактивного анализа и визуализации научных публикаций на основе метаданных из открытых источников.

**Задачи:**
1. Загрузить метаданные публикаций из API OpenAlex.
2. Разработать реляционную базу данных PostgreSQL для их хранения.
3. Выполнить геокодирование организаций авторов.
4. Реализовать интерактивную карту с географией публикаций.
5. Реализовать граф связей: публикации — авторы — журналы — темы — аффилиации.
6. Разработать серверный API и веб-интерфейс.

Данные получены из OpenAlex — бесплатного каталога с более чем 250 миллионами работ. Для каждой публикации используются метаданные: название, авторы, год, аффилиации, тематические классификаторы, ключевые слова, DOI. Полные тексты статей не используются — структурированных описаний достаточно для выявления связей между участниками научного процесса.

Публикации существуют в виде разрозненных записей. Без специальных инструментов трудно понять, кто из авторов занимается смежными темами, откуда приходят исследования, как связаны журналы и авторские коллективы. Два визуальных инструмента решают эту задачу по-разному:

| Инструмент | Что показывает |
|---|---|
| **Карта** | Географию аффилиаций авторов — откуда в мире ведутся исследования |
| **Граф связей** | Связи между публикациями, авторами, журналами и темами |

## ГЛАВА I. ЗАГРУЗКА ДАННЫХ ИЗ OPENALEX

### 1.1. Источник данных

Данные загружаются из OpenAlex — открытого каталога научных работ организации OurResearch. Сервис бесплатный, регистрация не нужна, ограничение — не более 10 запросов в секунду (polite limit).

Общая схема получения данных:
```
[OpenAlex API] → [scripts/import.py] → [article_data.json] → [openalex_data/]
```

### 1.2. Скрипт загрузки: scripts/import.py

Скрипт обращается к эндпоинту `/works` и постранично скачивает публикации: до 200 записей на страницу, до 50 страниц за запуск — итого не более 10 000 статей.

Для каждой публикации извлекается:
- название, год публикации, DOI;
- журнал (`primary_location.source.display_name`);
- авторы и их аффилиации (`authorships`);
- тематические классификаторы (`topics`) и ключевые слова (`keywords`).

Навигация между страницами реализована через **cursor pagination** — механизм, при котором каждый ответ API содержит токен `next_cursor` для получения следующей страницы. Это позволяет обходить большие наборы данных без пропусков и дублирований.

Результат сохраняется в `article_data.json`, сгруппированный по журналам:

```json
[
  {
    "journal": "Nature",
    "articles": [
      {
        "id": "W2741809807",
        "display_name": "Attention is all you need",
        "publication_year": 2017,
        "authorships": [
          {
            "author": { "display_name": "Ashish Vaswani" },
            "institutions": [
              { "display_name": "Google Brain", "id": "I1299303" }
            ]
          }
        ]
      }
    ]
  }
]
```

При сбое соединения скрипт использует ранее сохранённый `article_data.json`, что позволяет не начинать загрузку заново.

### 1.3. Структура проекта и README

Все файлы проекта организованы по назначению. Структура описана в `README.md`:

```

│   ├── vkr1_app.js             # Логика приложения

├── scripts/
```

## ГЛАВА II. БАЗА ДАННЫХ

### 2.1. Выбор СУБД

Для хранения данных выбрана PostgreSQL — реляционная СУБД с открытым исходным кодом. Реляционная модель подходит для этого проекта, потому что между сущностями (публикации, авторы, журналы, аффилиации) есть чёткие связи — один журнал содержит много статей, одна статья имеет много авторов и т.д.

### 2.2. Конфигурация подключения: pg_config.py

Настройки подключения к базе данных вынесены в отдельный файл `pg_config.py`:

```python
PG_CONFIG = {
    "host": "localhost",
    "port": 5432,
    "dbname": "openalex_db",
    "user": "postgres",
    "password": "ваш_пароль",
    "client_encoding": "utf8",
}
```

Параметр `client_encoding: utf8` обязателен при работе на Windows: без него PostgreSQL возвращает сообщения об ошибках в кодировке cp1251, что приводит к `UnicodeDecodeError` в Python. Все скрипты проекта импортируют этот файл и подключаются через него — настройки меняются в одном месте.

### 2.3. Схема базы данных

База состоит из семи таблиц:

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `journals` | Научные журналы | `journal_id`, `openalex_id`, `name`, `issn`, `publisher` |
| `publications` | Публикации | `publication_id`, `title`, `doi`, `publication_year`, `abstract`, `journal_id` |
| `persons` | Авторы | `person_id`, `openalex_id`, `full_name`, `orcid` |
| `affiliations` | Организации авторов с геокоординатами | `affiliation_id`, `person_id`, `institution`, `country`, `latitude`, `longitude` |
| `publication_authors` | Связь публикация — автор | `publication_id`, `person_id`, `author_position` |
| `publication_topics` | Тематические классификаторы | `id`, `publication_id`, `topic_name`, `score` |
| `publication_keywords` | Ключевые слова | `id`, `publication_id`, `keyword_name`, `score` |

**Связи:**
- `journals` → `publications`: один журнал — много публикаций (1:N);
- `publications` ↔ `persons`: многие публикации имеют многих авторов (N:M через `publication_authors`);
- `persons` → `affiliations`: один автор может работать в нескольких организациях (1:N);
- `publications` → `publication_topics`, `publication_keywords`: одна публикация — несколько тем и слов (1:N).

### 2.4. Скрипты создания и загрузки

**Создание схемы:**
```bash
createdb -U postgres openalex_db
psql -U postgres -d openalex_db -f database/db.sql
```

**Загрузка данных из JSON:**
```bash
python database/setup_pg_database.py
```

Поскольку файл `article_data.json` весит более 200 МБ и не помещается в память целиком, используется библиотека `ijson` для потокового чтения — объект за объектом, без загрузки всего файла.

При вставке публикаций используются savepoint-ы на случай конфликтов уникальных ключей (например, два объекта OpenAlex ссылаются на один DOI):

```python
cur.execute("SAVEPOINT pub_save")
try:
    cur.execute("INSERT ... ON CONFLICT (openalex_id) DO UPDATE ...", ...)
    cur.execute("RELEASE SAVEPOINT pub_save")
except Exception:
    cur.execute("ROLLBACK TO SAVEPOINT pub_save")
```

Блок-схема загрузки:
```
[article_data.json]
        │
        ▼
[setup_pg_database.py]
        │
        ├──► journals          (INSERT по openalex_id)
        ├──► publications      (INSERT, journal_id из journals)
        ├──► persons           (INSERT по openalex_id)
        ├──► affiliations      (INSERT для каждой организации)
        ├──► publication_authors
        ├──► publication_topics
        └──► publication_keywords
```

**Результат:** в базу загружено **9 994 публикации**.

### 2.5. Серверный API

Доступ к данным — через Python-сервер `openalex_server.py` на стандартной библиотеке `http.server`:

| Эндпоинт | Описание |
|---|---|
| `GET /api/articles` | Список публикаций с авторами, темами, аффилиациями |
| `GET /api/article/{id}` | Детали публикации (аннотация, DOI) |
| `GET /api/stats` | Счётчики по таблицам |
| `GET /api/data-tables` | Полные данные всех таблиц |

Ответы сжимаются gzip, если клиент передаёт заголовок `Accept-Encoding: gzip`. Объём передаваемых данных сокращается в 5–10 раз.

## ГЛАВА III. ГЕОГРАФИЧЕСКАЯ ПРИВЯЗКА

### 3.1. Что такое геоданные

Геоданные — это данные с географической привязкой: координаты (широта и долгота), названия мест, страны. В этом проекте геоданные — координаты организаций, в которых работают авторы статей. Именно они позволяют поставить точку на карте.

| Понятие | Пример |
|---|---|
| Аффилиация | «MIT, Cambridge, USA» |
| Широта | 42.3601 |
| Долгота | −71.0942 |
| Результат | Точка на карте в Бостоне |

В OpenAlex координаты не идут вместе с публикациями — их нужно запрашивать отдельно через API организаций или геокодер.

### 3.2. Откуда берутся координаты: два источника

Геокодирование проходит в два этапа, потому что не все аффилиации в базе устроены одинаково. Часть из них имеет `institution_id` — ссылку на запись в каталоге OpenAlex. Для таких можно запросить координаты напрямую. Остальные записаны только строкой названия — и для них нужен геокодер по тексту.

**Источник 1 — OpenAlex Institutions API** (`geocoding/fetch_geo.py`)

Скрипт собирает все уникальные `institution_id` из таблицы `affiliations` и запрашивает их батчами по 100 штук:

```
GET https://api.openalex.org/institutions?filter=ids.openalex:I123|I456|...&select=id,geo
```

OpenAlex возвращает JSON с полями `geo.latitude` и `geo.longitude` для каждого учреждения. Между батчами — пауза 0,5 секунды, чтобы не превысить лимит API. Результаты сохраняются в кэш `geo_cache.json` — при повторном запуске скрипта уже обработанные ID не запрашиваются заново.

**Результат первого этапа:** координаты получены для **7 822 из 9 994 публикаций (78%)**.

Оставшиеся 22% — это публикации, у всех авторов которых аффилиации записаны только строкой без `institution_id`.

**Источник 2 — Photon (OpenStreetMap)** (`geocoding/fetch_geo_nominatim.py`)

Для строковых аффилиаций используется геокодер Photon от Komoot — бесплатный сервис на основе данных OpenStreetMap. Запрос:

```
GET https://photon.komoot.io/api/?q=<название организации>&limit=1
```

Поскольку строки аффилиаций часто длинные и содержат лишнее («Department of Physics, University of Tokyo, Japan»), скрипт применяет стратегию сокращения: пробует сначала полную строку, потом последние три части через запятую, потом две. Как только геокодер вернул результат — берётся первый вариант.

Важная деталь: Photon возвращает координаты в формате GeoJSON — порядок `[longitude, latitude]`, а не `[latitude, longitude]`. При сохранении они переставляются: `lat = coords[1], lon = coords[0]`.

Порядок обработки строк выбирается не случайно: сначала обрабатываются те организации, которые встречаются у авторов наибольшего числа публикаций без координат. Это позволяет максимально быстро увеличить покрытие карты.

Исходно планировалось использовать Nominatim (геокодер OpenStreetMap), но после нескольких прогонов сервис вернул HTTP 403 — IP был заблокирован за превышение допустимой частоты запросов. Переход на Photon решил проблему.

**Результат второго этапа:** геокодировано 229 из 257 строк аффилиаций, обновлено 410 записей. Покрытие выросло до **8 077 из 9 994 публикаций (80,8%)**.

### 3.4. Какие проблемы возникли при геокодировании

| Проблема | Причина | Решение |
|---|---|---|
| Часть аффилиаций без `institution_id` | OpenAlex не всегда возвращает ID | Геокодирование по строке через Photon |
| Nominatim заблокировал IP с HTTP 403 | Превышение лимита запросов | Переход на Photon |
| Координаты в порядке [lon, lat] | Формат GeoJSON | Перестановка при сохранении |
| Дублирующиеся записи | Разные строки одной организации | Дедупликация перед вставкой |

Блок-схема геокодирования:
```
[affiliations в БД]
        │
        ▼
[Уникальные institution_id]
        │
        ▼
[Запрос к OpenAlex /institutions (батчи по 100)]
        │
        ├── координаты найдены → сохранить в БД и кэш
        └── не найдены → перейти к Photon по строке названия
                │
                ▼
        [Photon: полная строка → 3 части → 2 части]
                │
                ▼
        [Сохранить координаты в БД]
```

## ГЛАВА IV. ИНТЕРФЕЙС И ВИЗУАЛИЗАЦИЯ ДАННЫХ

### 4.1. Структура интерфейса

Приложение — одностраничный HTML-документ (`interface/VKR1.html`) с тремя колонками:

- **Левая панель** — фильтры (год, журнал, автор, аффилиация), список статей, кнопки переключения режимов;
- **Центральная область** — карта или граф, переключается кнопками;
- **Правая панель** — детали выбранной статьи, список похожих, контекст связей;
- **Нижняя секция** — управление базой: импорт, экспорт, статистика.

Интерфейс поддерживает светлую и тёмную тему. Переключение сохраняется в `localStorage`. Все цвета задаются через CSS-переменные, поэтому тема меняется без перезагрузки страницы.

### 4.2. Карта

Карта строится через Plotly (`scatter_geo`). Каждая точка — аффилиация автора с известными координатами. На одну публикацию берётся не более пяти точек. Клик по точке открывает детали статьи в правой панели. При изменении фильтров карта перестраивается автоматически. Цвета суши, океана и границ подстраиваются под тему интерфейса.

### 4.3. Фасетная фильтрация

Четыре выпадающих списка (год, журнал, автор, аффилиация) работают в связке: при выборе значения в одном фильтре остальные показывают только те варианты, которые остались доступными. Это исключает ситуацию, когда комбинация фильтров не даёт ни одного результата.

### 4.4. Детали статьи

При выборе публикации правая панель показывает название, год, журнал, авторов, аффилиации, темы и ключевые слова. Аннотация и DOI загружаются отдельным запросом к серверу — только по требованию, чтобы не тянуть лишние данные при загрузке списка.

### 4.5. Оптимизация производительности

При работе с 10 000 статей несколько операций создавали зависания браузера. Устранены четыре проблемы:

- Тяжёлые операции (карта, граф) вынесены в `requestAnimationFrame` — не блокируют UI;
- При открытии страницы сразу показываются демо-данные, реальные загружаются в фоне;
- `flatMap` по всем авторам заменён на ленивый генератор;
- Подсчёт всех попарных связей статей (`O(n²)` — 50 млн операций для 10 тыс. статей) убран из постоянного расчёта.

## ГЛАВА V. ГРАФ СВЯЗЕЙ

### 5.1. Откуда берутся данные для графа

Когда пользователь открывает вкладку «Граф», браузер уже имеет загруженный список статей с метаданными. Из этого списка JavaScript-код строит граф прямо в памяти браузера — сервер не делает никаких дополнительных запросов специально для графа.

Из каждой статьи извлекаются:
- год публикации → узлы-годы;
- название журнала → узлы-журналы;
- список авторов → узлы-авторы;
- список аффилиаций авторов → узлы-аффилиации;
- сама статья → узел-статья.

Рёбра строятся по принципу: если две сущности связаны через одну публикацию — между ними проводится линия. Например, статья за 2021 год в журнале Nature с двумя авторами из MIT даст рёбра: 2021→статья, статья→Nature, статья→автор1, статья→автор2, автор1→MIT, автор2→MIT.

### 5.2. Как строится раскладка

Граф рисуется в SVG-элементе прямо в браузере — без внешних библиотек. Физической симуляции нет. Вместо неё используется **колоночная раскладка**: каждый тип узла получает свою вертикальную колонку, внутри которой узлы распределяются равномерно по высоте.

Шаги построения:
1. Для каждой колонки собирается список уникальных узлов.
2. Высота SVG вычисляется по самой длинной колонке: `height = 150 + кол-во узлов × 68px`.
3. Каждому узлу назначаются координаты: `x` — центр колонки, `y` — равномерно по высоте.
4. Рёбра рисуются как кривые Безье между центрами прямоугольников узлов.
5. Узел выбранной статьи подсвечивается рамкой цвета акцента, связанные рёбра становятся ярче.

Ширина SVG подбирается под режим: для полного графа с пятью колонками — 1500px, для остальных — 1300px. Минимальная высота — 560px. При большем количестве узлов SVG растягивается вертикально, а область прокручивается.

### 5.3. Типы узлов и режимы

| Тип узла | Что означает |
|---|---|
| Год | Год публикации |
| Журнал | Название журнала |
| Статья | Публикация |
| Автор | Имя автора |
| Аффилиация | Организация автора |

Пять режимов отображения позволяют смотреть на данные с разных сторон:

| Режим | Колонки | Что даёт |
|---|---|---|
| Полный граф | Год → Журнал → Статья → Автор → Аффилиация | Полная картина всех связей |
| Годы + журналы + статьи | Год → Журнал → Статья | Хронология и журнальная принадлежность |
| Авторы | Статья → Автор | Кто написал что, соавторства |
| Аффилиации | Статья → Аффилиация | Какие организации в каких работах |
| Похожие статьи | Статья — Статья | Тематически близкие публикации |

Клик на узел-статью открывает детали в правой панели. Одновременно отображается не более 70 статей — иначе граф становится нечитаемым.

## ГЛАВА VI. ПОИСК ПОХОЖИХ СТАТЕЙ

### 6.1. Как работает поиск

Когда пользователь кликает на статью, приложение перебирает все остальные статьи в текущем отфильтрованном наборе и для каждой считает балл сходства с выбранной. Это происходит в браузере, без запросов к серверу — все нужные данные уже загружены.

Алгоритм для каждой пары (выбранная статья A, кандидат B):

1. Находятся общие авторы: пересечение множеств `A.authors ∩ B.authors`.
2. Находятся общие темы: `A.topics ∩ B.topics`.
3. Находятся общие ключевые слова: `A.keywords ∩ B.keywords`.
4. Находятся общие аффилиации: `A.affiliations ∩ B.affiliations`.
5. Проверяется, одинаковый ли журнал.
6. Считается балл:

```
score = (общих авторов × 4)
      + (общих тем × 3)
      + (общих ключевых слов × 2)
      + (общих аффилиаций × 2)
      + (один журнал → +2)
```

Статьи сортируются по убыванию балла. Те, у кого `score = 0`, в список не попадают.

### 6.2. Почему такие веса

| Признак | Вес | Почему |
|---|---|---|
| Общие авторы | 4 | Один автор пишет тематически связанные работы |
| Общие темы | 3 | Главный содержательный признак близости |
| Общие ключевые слова | 2 | Уточняющий признак |
| Общие аффилиации | 2 | Соавторство из одной организации |
| Один журнал | 2 | Публикуются в одном издании |

Авторы получили наибольший вес, потому что один человек обычно работает в одной предметной области и его статьи содержательно близки. Темы из OpenAlex — более широкие классификаторы, чем ключевые слова, поэтому их вес выше.

### 6.3. Нормализация при сравнении

Перед сравнением все строки (имена авторов, ключевые слова, названия организаций) приводятся к нижнему регистру и обрезаются пробелы по краям. Без этого «MIT» и «mit» или «Machine Learning » и «machine learning» считались бы разными значениями и совпадения терялись.

### 6.4. Где результат виден

- **Правая панель**: при выборе статьи показывает ранжированный список похожих с баллом и перечнем совпадений — что именно совпало (авторы, темы и т.д.).
- **Режим графа «Похожие статьи»**: рёбра между статьями показывают связи, на рёбрах подписи с типами совпадений и баллом.

## ГЛАВА VII. ПРОБЛЕМЫ В ХОДЕ РАЗРАБОТКИ

### 7.1. Файл 201 МБ не прошёл в GitHub

GitHub не принимает файлы больше 100 МБ. Файл `article_data.json` с загруженными статьями весил 201 МБ — при попытке `git push` операция прерывалась с ошибкой.

Файл удалён из истории репозитория через `git filter-branch` и добавлен в `.gitignore`. Для передачи состояния базы используется дамп PostgreSQL (`dump.sql`).

### 7.2. Конфликты при слиянии веток

При параллельной работе в нескольких ветках возникали конфликты в файлах `vkr1_app.js` и документации. Git не мог автоматически выбрать нужную версию.

Конфликты решались командой `git checkout --theirs` — принять версию из удалённого репозитория как актуальную.

### 7.3. Браузер обрывал соединение при загрузке данных

При запросе `/api/articles` браузер прерывал соединение с ошибкой `ConnectionAbortedError: [WinError 10053]`. Причина — слишком большой JSON-ответ, который браузер не успевал принять.

В сервер добавлено gzip-сжатие: если клиент поддерживает `Accept-Encoding: gzip`, данные сжимаются перед отправкой. Объём ответа уменьшился в 5–10 раз.

### 7.4. Заканчивалось место на диске

Несколько раз во время работы с git на Windows диск заполнялся до нуля. Операции `git add`, `git commit` и временные файлы завершались с ошибкой `No space left on device`.

Решение — очистка временных файлов Windows (`%temp%`). После освобождения места работа продолжалась без изменений.

### 7.5. Часть аффилиаций без координат

Не все организации в OpenAlex имеют `institution_id` — часть записана только строкой названия. Для таких запрос к `/institutions` невозможен.

Написан резервный скрипт на основе геокодера Photon (OpenStreetMap): принимает строку названия, возвращает координаты. При этом исходный геокодер Nominatim заблокировал IP после нескольких прогонов — именно поэтому пришлось перейти на Photon.

### 7.6. Кодировка cp1251 на Windows

При запуске Python-скриптов PostgreSQL возвращал сообщения об ошибках в кодировке cp1251, Python ожидал UTF-8 — в результате `UnicodeDecodeError`.

Решение: `client_encoding: utf8` в `pg_config.py` и `sys.stdout.reconfigure(encoding='utf-8')` в скриптах, работающих с выводом на экран.

### 7.7. Страница зависала при подсчёте связей

Функция `buildAllConnections` считала все попарные связи между статьями. Для 10 000 статей это ~50 миллионов операций — вкладка браузера зависала на несколько минут.

Счётчик убран из постоянного расчёта. Связи вычисляются только при выборе конкретной статьи пользователем.
