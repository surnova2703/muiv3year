# ВЫПУСКНАЯ КВАЛИФИКАЦИОННАЯ РАБОТА

## Визуализация науки на основе метаданных публикаций и журналов

---

## АННОТАЦИЯ

Работа посвящена разработке веб-приложения для анализа и визуализации научных публикаций по метаданным из открытых источников. В ходе работы была решена задача автоматической загрузки данных через API OpenAlex, создана реляционная база данных PostgreSQL, выполнено геокодирование организаций авторов, реализованы интерактивная карта и граф связей, а также серверный API и браузерный интерфейс. Итогом стало работающее веб-приложение, позволяющее рассматривать набор научных публикаций с двух сторон: как географическую карту организаций авторов и как граф связей между публикациями, авторами, журналами и темами.

**Ключевые слова:** визуализация данных, научные публикации, OpenAlex, PostgreSQL, геокодирование, граф связей, веб-приложение.

---

## ВВЕДЕНИЕ

### Актуальность

По данным каталога OpenAlex, в открытом доступе сейчас находится более 250 миллионов научных работ. Борнманн и Мутц в 2014 году подсчитали, что в период с 1980 по 2012 год число публикаций удваивалось примерно каждые девять лет — это около 8–9% в год. Когда статей так много, привычный поиск по ключевым словам хорошо справляется с задачей «найти конкретную статью», но плохо подходит, если нужно понять что-то на уровне области: кто с кем сотрудничает, откуда приходят исследования по теме, как она развивалась со временем.

Карта и граф дают другую точку зрения на те же данные. Метаданные публикации — название, авторы, их организации, год, журнал, тематические классификаторы — позволяют построить оба представления без доступа к полному тексту статьи. Именно это и составляет основу данного проекта.

### Постановка задачи

**Объект исследования** — метаданные научных публикаций и журналов из открытых библиографических каталогов.

**Предмет исследования** — методы интерактивной визуализации этих метаданных: географическая карта аффилиаций авторов и граф связей между публикациями, авторами, журналами и организациями.

**Цель работы** — разработать веб-приложение для интерактивного анализа и визуализации научных публикаций на основе открытых метаданных.

Для достижения цели были поставлены следующие задачи:
1. Загрузить метаданные публикаций из API OpenAlex.
2. Разработать реляционную базу данных PostgreSQL для их хранения.
3. Выполнить геокодирование организаций авторов.
4. Реализовать интерактивную карту с географией публикаций.
5. Реализовать граф связей: публикации — авторы — журналы — темы — аффилиации.
6. Разработать серверный API и веб-интерфейс.

Ориентиры качества заданы заранее: покрытие геокодирования — не менее 75%; граф отображается без зависания браузера при наборе до 70 статей; фасетные фильтры гарантируют отсутствие пустых выборок; алгоритм поиска похожих статей учитывает не менее трёх независимых признаков с обоснованными весами.

### Глоссарий

| Термин | Определение |
|---|---|
| **Метаданные публикации** | Структурированное описание статьи: название, авторы, год, журнал, DOI, тематики, ключевые слова — без полного текста |
| **OpenAlex** | Открытый бесплатный каталог научных публикаций организации OurResearch; содержит более 250 млн работ |
| **API (Application Programming Interface)** | Интерфейс программного взаимодействия; здесь — набор HTTP-запросов для получения данных из OpenAlex |
| **DOI (Digital Object Identifier)** | Уникальный цифровой идентификатор научной публикации в формате 10.XXXX/... |
| **Аффилиация** | Организация, с которой связан автор на момент публикации (университет, институт, компания) |
| **Геокодирование** | Процесс определения географических координат (широта, долгота) по названию места или идентификатору организации |
| **Граф** | Математическая структура из узлов (вершин) и рёбер (связей) между ними; используется для визуализации отношений |
| **REST API** | Архитектурный стиль веб-сервисов, где каждый ресурс доступен по URL через стандартные HTTP-методы |
| **PostgreSQL** | Реляционная система управления базами данных с открытым исходным кодом |
| **Фасетная фильтрация** | Метод фильтрации, при котором параметры фильтров взаимозависимы: выбор в одном фильтре автоматически ограничивает варианты в других |
| **SVG (Scalable Vector Graphics)** | XML-формат для векторной графики в браузере; используется для рисования графа без внешних библиотек |
| **Cursor pagination** | Метод постраничного обхода данных через токены-курсоры, исключающий пропуски при изменении набора |
| **Балл сходства (similarity score)** | Числовая мера близости двух публикаций, вычисляемая по взвешенной сумме совпадающих признаков |

---

Данные получены из OpenAlex — бесплатного каталога с более чем 250 миллионами работ. Для каждой публикации берутся метаданные: название, авторы, год, аффилиации, тематические классификаторы, ключевые слова, DOI. Полные тексты статей в проекте не используются — структурированных описаний достаточно, чтобы выявить связи между участниками научного процесса.

Публикации сами по себе существуют как разрозненные записи. Без специальных инструментов трудно понять, кто из авторов занимается смежными темами, откуда приходят исследования, как связаны журналы и авторские коллективы. Два визуальных представления решают эту задачу с разных сторон:

| Инструмент | Что показывает |
|---|---|
| **Карта** | Географию аффилиаций авторов — откуда в мире ведутся исследования |
| **Граф связей** | Структурные связи между публикациями, авторами, журналами и темами |

## ГЛАВА I. ОБЗОР СУЩЕСТВУЮЩИХ РЕШЕНИЙ

Прежде чем начать разработку, было изучено несколько существующих инструментов для библиометрического анализа и визуализации публикаций. Ниже приведён обзор девяти систем, актуальных на 2024–2025 год, с анализом их возможностей и ограничений.

### 1.1. VOSviewer

VOSviewer — бесплатная программа для построения и визуализации библиометрических сетей, разработанная Лейденским университетом (Нидерланды). Распространяется как настольное приложение для Windows, macOS и Linux.

**Визуализации:** сети соавторства, совместного цитирования, библиографического сочетания, совместного употребления ключевых слов; карты плотности и наложения. Поддерживает отображение географии сотрудничества по странам.

**Источники данных:** Web of Science, Scopus, PubMed, Dimensions, Semantic Scholar. Данные необходимо подготовить и экспортировать в поддерживаемом формате заранее — встроенного поиска нет.

**Ограничения:** отсутствует алгоритм поиска похожих статей; фильтрация ограничена — применяется к уже загруженному набору; установка на компьютер обязательна; веб-версия (VOSviewer Online) требует сохранения данных в облаке.

### 1.2. CiteSpace

CiteSpace — бесплатное Java-приложение для анализа тенденций и структурных паттернов в научной литературе, разработано в Университете Дрексела (США).

**Визуализации:** сети цитирования с выделением всплесков активности (burst detection), кластерная раскладка с автоматическими метками, карты географического сотрудничества по странам (экспорт в KML для Google Earth).

**Источники данных:** Web of Science, Scopus, Dimensions, Lens.org, PubMed.

**Ограничения:** требует установки Java Runtime Environment; нет алгоритма похожих статей; интерфейс перегружен настройками и рассчитан на специалистов в области библиометрии; отсутствует веб-версия.

### 1.3. Connected Papers

Connected Papers — веб-сервис для визуального исследования тематических связей между статьями. Работает в браузере без установки. Базовый доступ бесплатный (5 графов в месяц), расширенный — от 6 долларов в месяц.

**Визуализации:** граф похожих статей, построенный на основе совместного цитирования и библиографического сочетания; отдельные режимы предшественников и производных работ.

**Алгоритм схожести:** учитывает совместное цитирование и сближение ссылок, приоритет отдаётся статьям близкого года публикации. Каждый граф строится вокруг одной выбранной статьи и охватывает до ~50 000 работ корпуса Semantic Scholar.

**Ограничения:** нет географической карты; одновременно анализируется только одна статья; нет фильтрации по авторам, аффилиациям или журналам; платная подписка для активного использования.

### 1.4. Bibliometrix / Biblioshiny

Bibliometrix — пакет для языка R с открытым исходным кодом (лицензия MIT), предназначенный для количественного анализа научной литературы. Biblioshiny — его веб-интерфейс на основе фреймворка Shiny, запускаемый локально.

**Визуализации:** карты соавторства по странам, сети ключевых слов, тематические карты, анализ продуктивности авторов, плотностные карты аффилиаций. Интерфейс Biblioshiny обеспечивает интерактивность.

**Источники данных:** Web of Science, Scopus, PubMed, OpenAlex (прямая интеграция через API), Lens.org, Dimensions.

**Ограничения:** требует установки R и запуска локального Shiny-сервера; нет поиска похожих статей; порог вхождения высок для пользователей без опыта программирования.

### 1.5. Gephi

Gephi — бесплатная программа с открытым кодом (лицензия GPL) для визуализации и анализа больших сетей. Версия 0.11 (май 2025 года) поддерживает до 10 миллионов элементов.

**Визуализации:** сетевые графы с настраиваемой раскладкой (force-directed, circular, geographic), визуализация центральности, кластеризация и модульность. Gephi Lite — ограниченная веб-версия.

**Ограничения:** данные необходимо предварительно подготовить в форматах GEXF, GraphML, CSV; нет встроенного подключения к источникам научных данных; нет географической карты; нет алгоритма схожести статей.

### 1.6. Lens.org

Lens.org — бесплатный веб-сервис для поиска и анализа научных публикаций и патентов. Содержит более 225 миллионов научных работ. Работает в браузере без регистрации.

**Визуализации:** распределение публикаций по времени, топ-институтов, географическая карта публикаций по странам, диаграммы по тематикам и авторам.

**Фильтрация:** по году, автору, журналу, теме, типу доступа. Зарегистрированные пользователи могут экспортировать до 50 000 записей.

**Ограничения:** нет алгоритма поиска похожих статей; нет графа связей между публикациями и авторами; инструменты визуализации ограничены агрегированными диаграммами, а не интерактивным исследованием отдельных статей.

### 1.7. ResearchRabbit

ResearchRabbit — бесплатный веб-сервис (researchrabbitapp.com), запущенный в 2020 году. Позиционируется как «Spotify для научных статей». По состоянию на 2025 год насчитывает более 1 миллиона зарегистрированных пользователей.

**Визуализации:** интерактивный граф связей на основе совместного цитирования, временная шкала публикаций, кластеры авторов, карта похожих работ.

**Алгоритм схожести:** строится на анализе цитирований из базы Semantic Scholar. Пользователь создаёт коллекции статей, система рекомендует похожие работы в режиме реального времени. Интегрируется с Zotero.

**Ограничения:** нет географической карты аффилиаций; нет фильтрации по организациям; алгоритм работает только с цитированиями — статьи без цитирований (новые работы) не учитываются; нет экспорта данных в структурированном формате.

### 1.8. Inciteful

Inciteful (inciteful.xyz) — бесплатный веб-инструмент (2021) для анализа связей между публикациями на основе графа цитирований из базы OpenAlex.

**Визуализации:** граф цитирований вокруг одной или нескольких статей; рейтинги статей по алгоритму PageRank применительно к подграфу; таблица «самых важных» работ в контексте запроса.

**Источники данных:** OpenAlex (открытый доступ без регистрации).

**Ограничения:** нет географической карты; нет поиска по авторам и аффилиациям; граф строится только вокруг явных цитирований — тематическая близость без цитирования не учитывается; нет фасетной фильтрации.

### 1.9. Litmaps

Litmaps (litmaps.com) — веб-сервис (2021, Новая Зеландия) для построения карт научной литературы с акцентом на визуализацию временно́й динамики цитирований. Freemium-модель: бесплатно до 5 карт, от 10 долларов в месяц для неограниченного доступа.

**Визуализации:** «seedmap» — карта цитирований вокруг одной или нескольких статей с временно́й осью; автоматическое обновление карты при появлении новых работ.

**Источники данных:** Semantic Scholar (более 200 млн работ).

**Ограничения:** нет географической карты аффилиаций; нет фильтрации по авторам или организациям; ограниченный бесплатный доступ; граф строится только на основе явных цитирований.

### 1.12. Выводы из обзора

Анализ показывает, что каждый из рассмотренных инструментов решает отдельные задачи визуализации, однако ни один не сочетает одновременно все нужные возможности.

VOSviewer и CiteSpace — мощные инструменты для сетевого анализа, но требуют установки и предварительной подготовки данных, не имеют алгоритма похожих статей. Connected Papers обладает алгоритмом схожести, но работает только с одной статьёй за раз, не имеет карты и фильтрации по авторам и аффилиациям. Bibliometrix интегрируется с OpenAlex, однако требует знания R и запуска локального сервера. Gephi обрабатывает огромные графы, но не имеет встроенного подключения к научным данным и географической карты. Lens.org предоставляет географическую карту и фильтрацию, но ограничен агрегированными диаграммами без возможности исследовать связи между отдельными статьями.

Разработанная система занимает нишу, которую никто из перечисленных не закрывает: она объединяет в одном браузерном интерфейсе **географическую карту с точными координатами организаций**, **граф связей с пятью режимами**, **фасетную фильтрацию** и **алгоритм поиска похожих статей по пяти признакам**. При этом не требует установки стороннего программного обеспечения и работает с данными, загруженными напрямую из OpenAlex.

## ГЛАВА II. АРХИТЕКТУРА СИСТЕМЫ

### 2.1. Общая структура

Система состоит из пяти модулей, выстроенных в цепочку обработки данных:

```
[OpenAlex API]
      │
      ▼
[Модуль сбора данных]        scripts/import.py
      │
      ▼
[Реляционная БД]             PostgreSQL, 7 таблиц
      │
      ├──► [Модуль геокодирования]    geocoding/fetch_geo.py
      │
      ▼
[Серверный модуль]           openalex_server.py  (REST API)
      │
      ▼
[Браузерный интерфейс]       VKR1.html + vkr1_app.js
```

| Модуль | Файл(ы) | Функция |
|---|---|---|
| Сбор данных | `scripts/import.py` | Загрузка публикаций из OpenAlex API |
| База данных | `database/db.sql`, `setup_pg_database.py` | Хранение метаданных, SQL-схема |
| Геокодирование | `geocoding/fetch_geo.py`, `fetch_geo_nominatim.py` | Получение координат аффилиаций |
| Серверный API | `openalex_server.py`, `pg_config.py` | HTTP-сервер, REST-эндпоинты, gzip |
| Интерфейс | `interface/VKR1.html`, `vkr1_app.js`, `vkr1_styles.css` | Карта, граф, фильтры, поиск похожих |

### 2.2. Обоснование выбора технологий

#### Язык программирования: Python

Python выбран для серверной части и скриптов. Стандартная библиотека содержит `http.server` и `json` — этого достаточно для HTTP-сервера без сторонних фреймворков. Из внешних зависимостей использованы только `psycopg2` для работы с PostgreSQL и `ijson` для потокового чтения JSON. Python распространён в научном сообществе, что упрощает дальнейшее сопровождение проекта.

#### СУБД: PostgreSQL

Между сущностями проекта (публикации, авторы, журналы, аффилиации) существуют чёткие реляционные связи: один журнал содержит множество статей, одна статья имеет множество авторов. Для фасетной фильтрации нужны JOIN-запросы с несколькими условиями — именно это хорошо умеют реляционные СУБД. SQLite отклонён из-за ограниченной поддержки параллельных запросов. MongoDB не рассматривался всерьёз: документо-ориентированная модель здесь не даёт никаких преимуществ перед реляционной, а структура данных вполне укладывается в таблицы.

#### Библиотека визуализации карты: Plotly

Plotly выбран для отображения географической карты (`scatter_geo`). У него есть встроенная поддержка проекций карты мира, интерактивность (hover, zoom, click) работает без дополнительного кода, интеграция в HTML-страницу через CDN занимает одну строку. Leaflet.js ориентирован на тайловые карты и не подходит для scatter-визуализации на мировой проекции; D3.js потребовал бы значительно больше кода для аналогичного результата.

#### Граф: чистый SVG без библиотек

Для графа связей выбрана ручная отрисовка в SVG без внешних библиотек — без D3, без Cytoscape.js. Причина простая: нужна **колоночная раскладка**, при которой каждый тип узла занимает предсказуемую вертикальную позицию. Стандартные физические симуляции (force-directed layout), применяемые в D3 и Cytoscape, при 70+ узлах дают хаотичную и трудночитаемую картину. Колоночная раскладка детерминирована и остаётся читаемой независимо от числа узлов — это принципиально важно для данного проекта.

#### Источник данных: OpenAlex

OpenAlex выбран вместо Semantic Scholar, Crossref или Scopus по нескольким причинам. Сервис бесплатный и не требует регистрации для большинства запросов. Метаданные полные: авторы, аффилиации с идентификаторами, тематические классификаторы и ключевые слова возвращаются в одном ответе. Cursor pagination обеспечивает надёжную выгрузку больших наборов данных без дублирований. Наконец, отдельный эндпоинт `/institutions` позволяет пакетно запрашивать координаты по идентификаторам — это ключевая возможность для первого этапа геокодирования.

### 2.3. Поток данных и взаимодействие модулей

Данные в системе проходят следующий путь:

1. **Сбор:** `import.py` делает запросы к `/works` по cursor pagination, извлекает поля и сохраняет в `article_data.json`.
2. **Загрузка в БД:** `setup_pg_database.py` читает JSON потоково (ijson), нормализует данные и вставляет в 7 таблиц PostgreSQL с savepoint-защитой от конфликтов.
3. **Геокодирование:** `fetch_geo.py` обогащает таблицу `affiliations` координатами — сначала через OpenAlex `/institutions`, затем через Photon по текстовой строке.
4. **Отдача данных:** `openalex_server.py` принимает HTTP-запросы, выполняет SQL-запросы с JOIN, сериализует результат в JSON, сжимает gzip и отправляет браузеру.
5. **Визуализация:** `vkr1_app.js` строит карту и граф из полученных данных в памяти браузера, обновляет при изменении фильтров, вычисляет похожие статьи без дополнительных запросов к серверу.

### 3.1. Источник данных

Данные загружаются из OpenAlex — открытого каталога научных работ организации OurResearch. Сервис бесплатный, регистрация не нужна, ограничение — не более 10 запросов в секунду (polite limit).

Общая схема получения данных:
```
[OpenAlex API] → [scripts/import.py] → [article_data.json] → [openalex_data/]
```

### 3.2. Скрипт загрузки: scripts/import.py

Скрипт обращается к эндпоинту `/works` и постранично скачивает публикации: до 200 записей на страницу, до 50 страниц за запуск — итого не более 10 000 статей.

Для каждой публикации извлекается:
- название, год публикации, DOI;
- журнал (`primary_location.source.display_name`);
- авторы и их аффилиации (`authorships`);
- тематические классификаторы (`topics`) и ключевые слова (`keywords`).

Навигация между страницами реализована через **cursor pagination** — механизм, при котором каждый ответ API содержит токен `next_cursor` для получения следующей страницы. Это позволяет обходить большие наборы данных без пропусков и дублирований.

Результат сохраняется в `article_data.json`, сгруппированный по журналам:

```json
[
  {
    "journal": "Nature",
    "articles": [
      {
        "id": "W2741809807",
        "display_name": "Attention is all you need",
        "publication_year": 2017,
        "authorships": [
          {
            "author": { "display_name": "Ashish Vaswani" },
            "institutions": [
              { "display_name": "Google Brain", "id": "I1299303" }
            ]
          }
        ]
      }
    ]
  }
]
```

При сбое соединения скрипт использует ранее сохранённый `article_data.json`, что позволяет не начинать загрузку заново.

## ГЛАВА IV. БАЗА ДАННЫХ

### 4.1. Выбор СУБД

Для хранения данных выбрана PostgreSQL — реляционная СУБД с открытым исходным кодом. Реляционная модель здесь естественна: между сущностями (публикации, авторы, журналы, аффилиации) есть чёткие связи — один журнал содержит много статей, одна статья имеет много авторов и т.д.

### 4.2. Конфигурация подключения: pg_config.py

Настройки подключения к базе данных вынесены в отдельный файл `pg_config.py`:

```python
PG_CONFIG = {
    "host": "localhost",
    "port": 5432,
    "dbname": "openalex_db",
    "user": "postgres",
    "password": "ваш_пароль",
    "client_encoding": "utf8",
}
```

Параметр `client_encoding: utf8` обязателен при работе на Windows: без него PostgreSQL возвращает сообщения об ошибках в кодировке cp1251, что приводит к `UnicodeDecodeError` в Python. Все скрипты проекта импортируют этот файл и подключаются через него — настройки меняются в одном месте.

### 4.3. Схема базы данных

База состоит из семи таблиц:

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `journals` | Научные журналы | `journal_id`, `openalex_id`, `name`, `issn`, `publisher` |
| `publications` | Публикации | `publication_id`, `title`, `doi`, `publication_year`, `abstract`, `journal_id` |
| `persons` | Авторы | `person_id`, `openalex_id`, `full_name`, `orcid` |
| `affiliations` | Организации авторов с геокоординатами | `affiliation_id`, `person_id`, `institution`, `country`, `latitude`, `longitude` |
| `publication_authors` | Связь публикация — автор | `publication_id`, `person_id`, `author_position` |
| `publication_topics` | Тематические классификаторы | `id`, `publication_id`, `topic_name`, `score` |
| `publication_keywords` | Ключевые слова | `id`, `publication_id`, `keyword_name`, `score` |

**Связи:**
- `journals` → `publications`: один журнал — много публикаций (1:N);
- `publications` ↔ `persons`: многие публикации имеют многих авторов (N:M через `publication_authors`);
- `persons` → `affiliations`: один автор может работать в нескольких организациях (1:N);
- `publications` → `publication_topics`, `publication_keywords`: одна публикация — несколько тем и слов (1:N).

### 4.4. Скрипты создания и загрузки

**Создание схемы:**
```bash
createdb -U postgres openalex_db
psql -U postgres -d openalex_db -f database/db.sql
```

**Загрузка данных из JSON:**
```bash
python database/setup_pg_database.py
```

Файл `article_data.json` весит более 200 МБ и не помещается в память целиком, поэтому используется библиотека `ijson` для потокового чтения — объект за объектом, без загрузки всего файла.

При вставке публикаций используются savepoint-ы на случай конфликтов уникальных ключей (например, когда два объекта OpenAlex ссылаются на один DOI):

```python
cur.execute("SAVEPOINT pub_save")
try:
    cur.execute("INSERT ... ON CONFLICT (openalex_id) DO UPDATE ...", ...)
    cur.execute("RELEASE SAVEPOINT pub_save")
except Exception:
    cur.execute("ROLLBACK TO SAVEPOINT pub_save")
```

Блок-схема загрузки:
```
[article_data.json]
        │
        ▼
[setup_pg_database.py]
        │
        ├──► journals          (INSERT по openalex_id)
        ├──► publications      (INSERT, journal_id из journals)
        ├──► persons           (INSERT по openalex_id)
        ├──► affiliations      (INSERT для каждой организации)
        ├──► publication_authors
        ├──► publication_topics
        └──► publication_keywords
```

**Результат:** в базу загружено **9 994 публикации**.

### 4.5. Серверный API

Доступ к данным — через Python-сервер `openalex_server.py` на стандартной библиотеке `http.server`:

| Эндпоинт | Описание |
|---|---|
| `GET /api/articles` | Список публикаций с авторами, темами, аффилиациями |
| `GET /api/article/{id}` | Детали публикации (аннотация, DOI) |
| `GET /api/stats` | Счётчики по таблицам |
| `GET /api/data-tables` | Полные данные всех таблиц |

Ответы сжимаются gzip, если клиент передаёт заголовок `Accept-Encoding: gzip`. Объём передаваемых данных сокращается в 5–10 раз.

## ГЛАВА V. ГЕОГРАФИЧЕСКАЯ ПРИВЯЗКА

### 5.1. Что такое геоданные

Геоданные — это данные с географической привязкой: координаты (широта и долгота), названия мест, страны. В этом проекте геоданные — координаты организаций, в которых работают авторы статей. Именно они позволяют поставить точку на карте.

| Понятие | Пример |
|---|---|
| Аффилиация | «MIT, Cambridge, USA» |
| Широта | 42.3601 |
| Долгота | −71.0942 |
| Результат | Точка на карте в Бостоне |

В OpenAlex координаты не идут вместе с публикациями — их нужно запрашивать отдельно через API организаций или геокодер.

### 5.2. Откуда берутся координаты: два источника

Геокодирование проходит в два этапа, потому что не все аффилиации в базе устроены одинаково. Часть из них имеет `institution_id` — ссылку на запись в каталоге OpenAlex. Для таких можно запросить координаты напрямую. Остальные записаны только строкой названия — и для них нужен геокодер по тексту.

**Источник 1 — OpenAlex Institutions API** (`geocoding/fetch_geo.py`)

Скрипт собирает все уникальные `institution_id` из таблицы `affiliations` и запрашивает их батчами по 100 штук:

```
GET https://api.openalex.org/institutions?filter=ids.openalex:I123|I456|...&select=id,geo
```

OpenAlex возвращает JSON с полями `geo.latitude` и `geo.longitude` для каждого учреждения. Между батчами — пауза 0,5 секунды, чтобы не превысить лимит API. Результаты сохраняются в кэш `geo_cache.json` — при повторном запуске скрипта уже обработанные ID не запрашиваются заново.

**Результат первого этапа:** координаты получены для **7 822 из 9 994 публикаций (78%)**.

Оставшиеся 22% — это публикации, у всех авторов которых аффилиации записаны только строкой без `institution_id`.

**Источник 2 — Photon (OpenStreetMap)** (`geocoding/fetch_geo_nominatim.py`)

Для строковых аффилиаций используется геокодер Photon от Komoot — бесплатный сервис на основе данных OpenStreetMap. Запрос:

```
GET https://photon.komoot.io/api/?q=<название организации>&limit=1
```

Поскольку строки аффилиаций часто длинные и содержат лишнее («Department of Physics, University of Tokyo, Japan»), скрипт применяет стратегию сокращения: пробует сначала полную строку, потом последние три части через запятую, потом две. Как только геокодер вернул результат — берётся первый вариант.

Важная деталь: Photon возвращает координаты в формате GeoJSON — порядок `[longitude, latitude]`, а не `[latitude, longitude]`. При сохранении они переставляются: `lat = coords[1], lon = coords[0]`.

Порядок обработки строк выбирается не случайно: сначала обрабатываются те организации, которые встречаются у авторов наибольшего числа публикаций без координат. Это позволяет максимально быстро увеличить покрытие карты.

Исходно планировалось использовать Nominatim (геокодер OpenStreetMap), но после нескольких прогонов сервис вернул HTTP 403 — IP был заблокирован за превышение допустимой частоты запросов. Переход на Photon решил проблему.

**Результат второго этапа:** геокодировано 229 из 257 строк аффилиаций, обновлено 410 записей. Покрытие выросло до **8 077 из 9 994 публикаций (80,8%)**.

### 5.3. Какие проблемы возникли при геокодировании

| Проблема | Причина | Решение |
|---|---|---|
| Часть аффилиаций без `institution_id` | OpenAlex не всегда возвращает ID | Геокодирование по строке через Photon |
| Nominatim заблокировал IP с HTTP 403 | Превышение лимита запросов | Переход на Photon |
| Координаты в порядке [lon, lat] | Формат GeoJSON | Перестановка при сохранении |
| Дублирующиеся записи | Разные строки одной организации | Дедупликация перед вставкой |

Блок-схема геокодирования:
```
[affiliations в БД]
        │
        ▼
[Уникальные institution_id]
        │
        ▼
[Запрос к OpenAlex /institutions (батчи по 100)]
        │
        ├── координаты найдены → сохранить в БД и кэш
        └── не найдены → перейти к Photon по строке названия
                │
                ▼
        [Photon: полная строка → 3 части → 2 части]
                │
                ▼
        [Сохранить координаты в БД]
```

## ГЛАВА VI. ИНТЕРФЕЙС И ВИЗУАЛИЗАЦИЯ ДАННЫХ

### 6.1. Структура интерфейса

Приложение — одностраничный HTML-документ (`interface/VKR1.html`) с тремя колонками:

- **Левая панель** — фильтры (год, журнал, автор, аффилиация), список статей, кнопки переключения режимов;
- **Центральная область** — карта или граф, переключается кнопками;
- **Правая панель** — детали выбранной статьи, список похожих, контекст связей;
- **Нижняя секция** — управление базой: импорт, экспорт, статистика.

Интерфейс поддерживает светлую и тёмную тему. Переключение сохраняется в `localStorage`. Все цвета задаются через CSS-переменные, поэтому тема меняется без перезагрузки страницы.

### 6.2. Карта

Карта строится через Plotly (`scatter_geo`). Каждая точка — аффилиация автора с известными координатами. На одну публикацию берётся не более пяти точек. Клик по точке открывает детали статьи в правой панели. При изменении фильтров карта перестраивается автоматически. Цвета суши, океана и границ подстраиваются под тему интерфейса.

### 6.3. Фасетная фильтрация

Четыре выпадающих списка (год, журнал, автор, аффилиация) работают в связке: при выборе значения в одном фильтре остальные показывают только те варианты, которые остались доступными. Это исключает ситуацию, когда комбинация фильтров не даёт ни одного результата.

### 6.4. Детали статьи

При выборе публикации правая панель показывает название, год, журнал, авторов, аффилиации, темы и ключевые слова. Аннотация и DOI загружаются отдельным запросом к серверу — только по требованию, чтобы не тянуть лишние данные при загрузке списка.

### 6.5. Оптимизация производительности

При работе с 10 000 статей несколько операций создавали зависания браузера. Устранены четыре проблемы:

- Тяжёлые операции (карта, граф) вынесены в `requestAnimationFrame` — не блокируют UI;
- При открытии страницы сразу показываются демо-данные, реальные загружаются в фоне;
- `flatMap` по всем авторам заменён на ленивый генератор;
- Подсчёт всех попарных связей статей (`O(n²)` — 50 млн операций для 10 тыс. статей) убран из постоянного расчёта.

## ГЛАВА VII. ГРАФ СВЯЗЕЙ

### 7.1. Откуда берутся данные для графа

Когда пользователь открывает вкладку «Граф», браузер уже имеет загруженный список статей с метаданными. Из этого списка JavaScript-код строит граф прямо в памяти браузера — сервер не делает никаких дополнительных запросов специально для графа.

Из каждой статьи извлекаются:
- год публикации → узлы-годы;
- название журнала → узлы-журналы;
- список авторов → узлы-авторы;
- список аффилиаций авторов → узлы-аффилиации;
- сама статья → узел-статья.

Рёбра строятся по принципу: если две сущности связаны через одну публикацию — между ними проводится линия. Например, статья за 2021 год в журнале Nature с двумя авторами из MIT даст рёбра: 2021→статья, статья→Nature, статья→автор1, статья→автор2, автор1→MIT, автор2→MIT.

### 7.2. Как строится раскладка

Граф рисуется в SVG-элементе прямо в браузере — без внешних библиотек. Физической симуляции нет. Вместо неё используется **колоночная раскладка**: каждый тип узла получает свою вертикальную колонку, внутри которой узлы распределяются равномерно по высоте.

Шаги построения:
1. Для каждой колонки собирается список уникальных узлов.
2. Высота SVG вычисляется по самой длинной колонке: `height = 150 + кол-во узлов × 68px`.
3. Каждому узлу назначаются координаты: `x` — центр колонки, `y` — равномерно по высоте.
4. Рёбра рисуются как кривые Безье между центрами прямоугольников узлов.
5. Узел выбранной статьи подсвечивается рамкой цвета акцента, связанные рёбра становятся ярче.

Ширина SVG подбирается под режим: для полного графа с пятью колонками — 1500px, для остальных — 1300px. Минимальная высота — 560px. При большем количестве узлов SVG растягивается вертикально, а область прокручивается.

### 7.3. Типы узлов и режимы

| Тип узла | Что означает |
|---|---|
| Год | Год публикации |
| Журнал | Название журнала |
| Статья | Публикация |
| Автор | Имя автора |
| Аффилиация | Организация автора |

Пять режимов отображения позволяют смотреть на данные с разных сторон:

| Режим | Колонки | Что даёт |
|---|---|---|
| Полный граф | Год → Журнал → Статья → Автор → Аффилиация | Полная картина всех связей |
| Годы + журналы + статьи | Год → Журнал → Статья | Хронология и журнальная принадлежность |
| Авторы | Статья → Автор | Кто написал что, соавторства |
| Аффилиации | Статья → Аффилиация | Какие организации в каких работах |
| Похожие статьи | Статья — Статья | Тематически близкие публикации |

Клик на узел-статью открывает детали в правой панели. Одновременно отображается не более 70 статей — иначе граф становится нечитаемым.

## ГЛАВА VIII. ПОИСК ПОХОЖИХ СТАТЕЙ

### 8.1. Как работает поиск

Когда пользователь кликает на статью, приложение перебирает все остальные статьи в текущем отфильтрованном наборе и для каждой считает балл сходства с выбранной. Это происходит в браузере, без запросов к серверу — все нужные данные уже загружены.

Алгоритм для каждой пары (выбранная статья A, кандидат B):

1. Находятся общие авторы: пересечение множеств `A.authors ∩ B.authors`.
2. Находятся общие темы: `A.topics ∩ B.topics`.
3. Находятся общие ключевые слова: `A.keywords ∩ B.keywords`.
4. Находятся общие аффилиации: `A.affiliations ∩ B.affiliations`.
5. Проверяется, одинаковый ли журнал.
6. Считается балл:

```
score = (общих авторов × 4)
      + (общих тем × 3)
      + (общих ключевых слов × 2)
      + (общих аффилиаций × 2)
      + (один журнал → +2)
```

Статьи сортируются по убыванию балла. Те, у кого `score = 0`, в список не попадают.

### 8.2. Почему такие веса

| Признак | Вес | Почему |
|---|---|---|
| Общие авторы | 4 | Один автор пишет тематически связанные работы |
| Общие темы | 3 | Главный содержательный признак близости |
| Общие ключевые слова | 2 | Уточняющий признак |
| Общие аффилиации | 2 | Соавторство из одной организации |
| Один журнал | 2 | Публикуются в одном издании |

Авторы получили наибольший вес, потому что один человек обычно работает в одной предметной области и его статьи содержательно близки. Темы из OpenAlex — более широкие классификаторы, чем ключевые слова, поэтому их вес выше. Веса подобраны эмпирически на реальных данных из базы.

### 8.3. Нормализация при сравнении

Перед сравнением все строки (имена авторов, ключевые слова, названия организаций) приводятся к нижнему регистру и обрезаются пробелы по краям. Без этого «MIT» и «mit» или «Machine Learning » и «machine learning» считались бы разными значениями и совпадения терялись.

### 8.4. Где результат виден

- **Правая панель**: при выборе статьи показывает ранжированный список похожих с баллом и перечнем совпадений — что именно совпало (авторы, темы и т.д.).
- **Режим графа «Похожие статьи»**: рёбра между статьями показывают связи, на рёбрах подписи с типами совпадений и баллом.

## ГЛАВА IX. ПРОБЛЕМЫ В ХОДЕ РАЗРАБОТКИ

### 9.1. Файл 201 МБ не прошёл в GitHub

GitHub не принимает файлы больше 100 МБ. Файл `article_data.json` с загруженными статьями весил 201 МБ — при попытке `git push` операция прерывалась с ошибкой.

Файл удалён из истории репозитория через `git filter-branch` и добавлен в `.gitignore`. Для передачи состояния базы используется дамп PostgreSQL (`dump.sql`).

### 9.2. Конфликты при слиянии веток

При параллельной работе в нескольких ветках возникали конфликты в файлах `vkr1_app.js` и документации. Git не мог автоматически выбрать нужную версию.

Конфликты решались командой `git checkout --theirs` — принять версию из удалённого репозитория как актуальную.

### 9.3. Браузер обрывал соединение при загрузке данных

При запросе `/api/articles` браузер прерывал соединение с ошибкой `ConnectionAbortedError: [WinError 10053]`. Причина — слишком большой JSON-ответ, который браузер не успевал принять.

В сервер добавлено gzip-сжатие: если клиент поддерживает `Accept-Encoding: gzip`, данные сжимаются перед отправкой. Объём ответа уменьшился в 5–10 раз.

### 9.4. Заканчивалось место на диске

Несколько раз во время работы с git на Windows диск заполнялся до нуля. Операции `git add`, `git commit` и временные файлы завершались с ошибкой `No space left on device`.

Решение — очистка временных файлов Windows (`%temp%`). После освобождения места работа продолжалась без изменений.

### 9.5. Часть аффилиаций без координат

Не все организации в OpenAlex имеют `institution_id` — часть записана только строкой названия. Для таких запрос к `/institutions` невозможен.

Написан резервный скрипт на основе геокодера Photon (OpenStreetMap): принимает строку названия, возвращает координаты. При этом исходный геокодер Nominatim заблокировал IP после нескольких прогонов — именно поэтому пришлось перейти на Photon.

### 9.6. Кодировка cp1251 на Windows

При запуске Python-скриптов PostgreSQL возвращал сообщения об ошибках в кодировке cp1251, Python ожидал UTF-8 — в результате `UnicodeDecodeError`.

Решение: `client_encoding: utf8` в `pg_config.py` и `sys.stdout.reconfigure(encoding='utf-8')` в скриптах, работающих с выводом на экран.

### 9.7. Страница зависала при подсчёте связей

Функция `buildAllConnections` считала все попарные связи между статьями. Для 10 000 статей это ~50 миллионов операций — вкладка браузера зависала на несколько минут.

Счётчик убран из постоянного расчёта. Связи вычисляются только при выборе конкретной статьи пользователем.

## ГЛАВА X. ТРЕБОВАНИЯ К СИСТЕМЕ

### 10.1. Назначение системы

Система предназначена для интерактивного исследования массивов научных публикаций. Целевая аудитория — исследователи, аспиранты и специалисты, которым требуется быстро ориентироваться в большом количестве публикаций по теме, выявлять географию исследований и находить тематически близкие работы.

### 10.2. Функциональные требования

Система должна выполнять следующие функции:

- загружать метаданные публикаций из OpenAlex API и сохранять в локальную базу данных;
- отображать интерактивную карту с точками аффилиаций авторов;
- отображать граф связей публикация — автор — журнал — аффилиация в пяти режимах;
- предоставлять фасетную фильтрацию по году, журналу, автору и аффилиации;
- при выборе публикации вычислять и показывать список похожих статей с объяснением совпадений;
- поддерживать переключение между светлой и тёмной темой с сохранением выбора;
- предоставлять REST API для доступа к данным;
- при отсутствии координат организации пытаться геокодировать её по текстовому названию.

### 10.3. Нефункциональные требования

Из нефункциональных требований ключевыми являются производительность и покрытие геокодирования. Граф с 70 статьями должен отображаться без зависания браузера — это ограничение выбрано исходя из читаемости: при большем числе узлов граф перестаёт быть понятным. Покрытие геокодирования — не менее 75% публикаций. Приложение должно запускаться на Windows и Linux без изменения кода, ответы API сжиматься gzip при поддержке клиентом.

### 10.4. Технические ограничения

- Одновременно в графе отображается не более 70 публикаций.
- Список статей в интерфейсе ограничен 200 записями на одну страницу.
- Полные тексты публикаций не загружаются и не хранятся — только метаданные.
- Приложение работает локально; развёртывание на публичный сервер не предусмотрено в текущей версии.

### 10.5. Среда выполнения

| Компонент | Требование |
|---|---|
| Операционная система | Windows 10/11 или Linux (Ubuntu 20.04+) |
| Python | Версия 3.9 или выше |
| PostgreSQL | Версия 14 или выше |
| Браузер | Chrome 90+, Firefox 88+, Edge 90+ |
| Зависимости Python | `psycopg2-binary`, `ijson` |
| Интернет-соединение | Требуется только на этапе загрузки данных из OpenAlex |

## ЗАКЛЮЧЕНИЕ

В ходе выпускной квалификационной работы разработано веб-приложение для анализа и визуализации научных публикаций по метаданным из OpenAlex.

Выполнено следующее. Написан скрипт загрузки данных через cursor pagination, который собрал **9 994 публикации** с полными метаданными. Спроектирована реляционная база данных PostgreSQL из **7 таблиц** со связями и ограничениями целостности; при загрузке использованы savepoint-ы для устойчивости к конфликтам уникальных ключей. Написан серверный API на Python с gzip-сжатием ответов. Геокодирование аффилиаций двумя методами — через OpenAlex Institutions API и через Photon — дало покрытие **80,8% (8 077 из 9 994 публикаций)** при пороге 75%. Реализована интерактивная карта на Plotly с поддержкой тёмной и светлой темы, граф связей с пятью режимами отображения в SVG без внешних библиотек, алгоритм поиска похожих статей по взвешенному баллу из пяти признаков, браузерный интерфейс с фасетной фильтрацией.

Все четыре критерия, заданных в начале работы, выполнены:

| Критерий | Целевое значение | Фактический результат |
|---|---|---|
| Покрытие геокодирования | ≥ 75% | **80,8%** (8 077 из 9 994) |
| Граф без зависания при 70 статьях | выполнено | ✓ (requestAnimationFrame, O(1) рендер) |
| Фасетные фильтры без пустых результатов | выполнено | ✓ (зависимые списки) |
| Алгоритм по ≥ 3 признакам | ≥ 3 признака | **5 признаков** (авторы, темы, ключевые слова, аффилиации, журнал) |

По сравнению с рассмотренными инструментами система объединяет в одной браузерной среде без установки то, что в остальных решениях разнесено по разным продуктам: географическую карту с точными координатами организаций, граф связей с несколькими режимами, фасетную фильтрацию и алгоритм поиска похожих, не основанный только на цитированиях.

Возможные направления дальнейшего развития: реализация полнотекстового поиска по аннотациям, добавление экспорта графа в форматы VOSviewer и Gephi, переход на серверный рендеринг графа для поддержки наборов свыше 10 000 публикаций.
